# PC 故障排查流程

查核日期：2026-10-12。範圍：Windows PC。這是可重用的調查架構，不代表已診斷截圖中的電腦。

## 從症狀出發

| 症狀 | 蒐集證據 | 第一輪調查 | 成功標準 |
| --- | --- | --- | --- |
| 藍畫面或非正常重啟 | 停止代碼、傾印、完整 41／6008／1001、負載與近期變更 | 以真正關機時間比對先前驅動／硬體事件，分析相符傾印 | 相當觀察期間內，原負載穩定 |
| 當機需長按電源 | 滑鼠／聲音／網路是否仍回應、持續時間、溫度與先前事件 | 區分僅顯示失敗或整台當機；一次測試一項有證據指向的變更 | 相同觸發條件不再當機，不需強制關機 |
| 黑畫面或顯示重置 | 顯示連接、GPU／驅動版本、受影響螢幕、Display 事件與 LiveKernelReports 清單 | 測試另一條線／埠；證據支持時測試受支援 GPU 驅動 | 相同負載下顯示持續可用 |
| 緩慢或風扇高速 | 工作管理員 CPU／記憶體／磁碟、可用空間、啟動程式及溫度 | 識別程式／資源瓶頸，量測前後差異 | 延遲／資源使用改善且功能正常 |
| 磁碟／I/O 錯誤或檔案遺失 | 備份狀態、磁碟型號／韌體、控制器事件及健康資料 | 修復或密集測試前先保留資料，檢查已識別裝置 | 資料可存取且完整性經確認，重複錯誤已解決 |
| 網路斷線 | Wi-Fi／Ethernet 範圍、網卡／驅動、路由器、其他裝置是否失敗 | 區分 PC、區網／路由器、DNS 與 ISP，測試其他連線 | 原本觸發條件下連線穩定 |
| USB／聲音斷線 | 裝置、集線器、埠、事件與可重現操作 | 一次測試一個裝置並繞過集線器，再測試其他埠／線 | 相同工作不中斷 |
| 程式崩潰、開始／搜尋失敗 | 執行檔／模組、例外、套件／操作、版本及報告 ID | 重現並修復已識別程式，適當時比較測試設定檔 | 原操作成功，崩潰循環結束 |
| 睡眠／喚醒問題 | 闔蓋／睡眠／休眠觸發、周邊、驅動與電源事件 | 相同循環下移除一項有證據指向的周邊／變更 | 多次循環成功且無非正常重啟 |

以上為建議診斷分支，不可由單一症狀或事件數量就判定故障元件。

## 變更前保留證據

1. 記錄 Windows 版本／組建（`winver`）、PC／主機板型號、CPU／GPU／RAM、儲存與供電配置，以及程式／驅動／BIOS 版本及近期變更。
2. 用白話記錄症狀：什麼不能使用、當時操作、是否藍畫面，以及是否強制關機。
3. 記錄裝置時區。事件檢視器通常顯示本機時間，XML `SystemTime` 是 UTC；截圖不能確定 UTC 偏移。
4. 匯出限定時間窗的 System、Application、Security 及相關程式／服務通道。資訊事件也要保留；Administrative Events 是彙整檢視，不是完整事故時間軸。
5. 保留相關提供者／ID 的「一般」及「詳細資料 → XML」。以提供者與 ID 一起比對，保留事前及正常運作對照；ID 不是全域唯一診斷。
6. 列出既有傾印，若分析需要則另行保留。日誌／傾印可能包含使用者名稱、路徑、裝置／租用戶識別或記憶體內容；分享前確認目的地，原始證據不要納入 Git。

在受影響 PC 手動執行 [Collect-Evidence.ps1](../scripts/Collect-Evidence.ps1)。工具只建立新證據目錄，查詢指定時間窗、保留 XML 並匯出 EVTX。不會執行修復、清除日誌、複製傾印內容或上傳資料。讀取 Security 可能需要系統管理員 PowerShell。缺少／停用通道及查詢／匯出失敗都記錄在 `manifest.json`；沒有事件標示 `no-events`，不會默默視為成功或失敗。

```powershell
# 使用受影響 PC 的明確時區偏移；下方 +08:00 僅為範例。
# 從本主題目錄執行，不會放寬執行原則。
.\scripts\Collect-Evidence.ps1 -Start '2026-10-03T17:20:00+08:00' -End '2026-10-03T18:50:00+08:00'
```

截圖時間窗只作初步候選；若 6008 記載更早的關機時間，需擴大範圍。認定沒有事件前先看 manifest。瀏覽頁呈現研究內容，不會自動讀取 PC 日誌。

## 有條件的修復

先保留證據並識別元件。一次只變更一項，記錄原設定／版本並保留回復方式。重啟或重設程式可能中斷工作，重設可能清除本機資料，應先匯出。韌體變更需確切型號及穩定電腦，不要只為減少警告就更新 BIOS。

證據指向 Windows 元件損毀或更新失敗時，官方修復順序是在系統管理員終端執行：

```powershell
DISM.exe /Online /Cleanup-Image /RestoreHealth
sfc.exe /scannow
```

這些會變更 Windows 元件，與證據蒐集分開。DISM 可能需要可用更新來源或相符修復來源；保留輸出並重新測試症狀。它們不能診斷 PSU／RAM／GPU 故障，也不是截圖的通用修法。[Microsoft 修復流程](https://learn.microsoft.com/en-us/troubleshoot/windows-server/installing-updates-features-roles/fix-windows-update-errors)。

驅動問題應先識別裝置，使用受支援 OEM／廠商套件；若故障在變更後開始，可用受控回復取得證據。硬體不穩定可先比較預設穩定設定與散熱，再使用已識別製造商的診斷。可疑磁碟應先備份再密集測試；記憶體／磁碟測試通過不代表排除所有間歇性故障。若持續資料遺失、硬體錯誤、過熱關機或穩定設定仍失敗，應送修。

避免登錄清理器、任意權限修改、停用稽核／安全功能、大量 AppX 重新註冊及未規劃的 Driver Verifier。修復須改善原症狀，隱藏警告不算驗證。

## 記錄個案

使用 [繁中個案範本](../cases/case-template.zh-TW.md) 或 [英文範本](../cases/case-template.md)。將去識別結論另存個案檔，原始證據留在忽略的 `evidence/`。註明來源，區分觀察與假設，記錄失敗和成功測試。對所有廠商（包含 EDT）使用相同證據標準。

以有意義的時間與負載比較基準，記錄事故頻率、成功重複次數、新事件及限制。若原本每週才出現，一天正常不足以確認修復。
