# 評估紀錄：三份提案、三位評審、一份融合建議

*截至 2026-10-05 的狀態 · 本紀錄說明[建議架構](recommended-architecture.zh-TW.md)與[主報告](../README.zh-TW.md)如何從提案 [A](proposal-A-lean-mvp.zh-TW.md)、[B](proposal-B-performance-core.zh-TW.md)、[C](proposal-C-platform-scale.zh-TW.md) 以及研究 [01](../research/01-core-language-runtime.zh-TW.md)–[11](../research/11-taiwan-market-localization.zh-TW.md) 推導而來。*

## 1. 方法

| 步驟 | 執行內容 |
|---|---|
| 輸入 | 11 份研究報告（每份皆附有日期為 2026-10-05 的對抗式驗證紀錄），以及 3 份針對不同團隊型態撰寫的架構提案：**A** 精實 MVP（1–3 人）、**B** 效能與正確性優先（5–20 人，含資深 Rust 工程師）、**C** 平台與規模化（6–12 人，多租戶） |
| 評審 | 三位獨立評審各自透過一個視角，以 0 到 10 分為三份提案評分，列出優點、缺點與致命缺陷，提出嫁接建議，並提出事實面的疑慮 |
| 主幹規則 | 選擇平均分數最高，**且**在使用者最可能的起始情境下沒有致命缺陷的提案：團隊規模未定，很可能是 1–3 人，自用 |
| 嫁接規則 | 若另一份提案或某位評審提出的元素能以低成本補上評審指出的缺口，或能建立一個低成本的接縫，使日後的演進路徑成為擴充而非重寫，則予以採納。任何會在其觸發條件成立之前就增加常態維運負擔的項目，一律延後 |
| 矛盾規則 | 研究報告彼此不一致時，以驗證紀錄、一手來源（套件登錄庫、授權檔案、法規條文）以及較新的日期為準。仍未驗證的項目則列為 Phase 0 檢查項目 |

## 3. 評審結論

### 3.1 可行性與交付（A 7.8 · B 3.0 · C 2.5）

**A 是唯一符合此視角規模的提案。** 它約以 10.5 人月（兩人約 6.5 個月）達到第一個實盤市場，因為 NautilusTrader 已提供 OMS、對帳、風控引擎，以及 IBKR 與加密貨幣的轉接器（adapter），團隊只需自行負責台灣轉接器。它的總體擁有成本也最低（在單一 Compose 主機上實盤約每月 $150–600），只需招募 Python 與 TypeScript 人才，且具備穩健的真實資金閘門。

**評審在 A 中發現的缺點：**

- **範圍。** M2–M4 階段把三個券商家族、雙時態（bitemporal）證券主檔、雜湊鏈結的日誌（journal）、MLflow 晉升把關、層級一致性檢查以及三個 UI 外殼，全部塞進約 6.5 人月，因此很可能延宕到 8–9 個月。
- **未列入登記冊的相依性風險。** NautilusTrader 的巴士係數（bus factor）約為 1，已宣布的 Nautilus Pro 方案暗示其走向 open-core，而 IB 路徑則依賴一個只有單一維護者的 `ibapi` crate。
- **維運。** 對單人營運者而言，24/7 的加密貨幣交易、IBKR 2FA、Shioaji 每 14 天一次的發版以及 RC 升級，負擔會不斷累積。
- **兩個 Python 映像檔**需要持續修補。

**B 與 C 依其自身的估算就無法通過此視角。**

**建議：** 以 A 為基準並縮減範圍（先做一個交易場所家族、先做 web 加 Telegram、採用較簡化的證券主檔），再以 B 的執行語意、確定性規則與終止準則，以及 C 的可部署單元規則、授權登記冊與精簡 SDK 加以強化。

*後續追蹤（2026-10-05）：* [主報告](../README.zh-TW.md)的路線圖後來考量此延宕風險，以由下而上的方式重新規劃。目前估計達到第一個實盤市場需要約 12 人月的基準工作量（加上 20–30% 的預備量則為 14–16 人月），兩人團隊約在第 8–9 個月首次實盤，且其成本表取代上述「$150–600/月」的數字。

### 3.2 正確性與效能（B 7.8 · A 6.5 · C 6.0）

**B 的設計最佳：**

- 由 CI 強制執行的確定性契約，以及經溢位檢查（checked）的定點數運算；
- 每次送單前寫入的日誌，以及在每種模式下位元組完全相同的 OMS 與風控閘門；
- 台灣集合競價與漲跌停鎖死的撮合；
- 真正的債券模型。

其風險在於自行打造的撮合器（對照基準（oracle）無法驗證新的台灣與債券邏輯），以及對 Python 策略過度承諾的跨作業系統位元一致保證。

**A 是近期內取得可信回測最可靠的途徑：** Nautilus 的確定性 i128 核心、每種模式皆使用相同的程式碼、嚴格的閘門，以及對自身缺口的坦誠。其缺點如下：

- 送單前沒有預寫紀錄（依賴非同步的 Valkey 持久化加上對帳）；
- 沒有公司行動（corporate action）事件，也沒有提前履約指派（early assignment）模型；
- 模擬器中的台灣撮合規則未經驗證；
- 由於指標實作不同，vectorbt 與 Nautilus 之間的層級一致性檢查雜訊偏高。

**C 具備強健的復原機制**，但其額外的網路跳轉與第二套訂單狀態機削弱了回測與實盤的一致性。它的模擬交易（paper）轉接器重複實作了模擬模型，而且它宣稱要在一個兩者皆不具備的引擎上建立債券與指派模型。

**三者共同的缺口：** 公司行動事件管線、由股利驅動的提前履約指派模型，以及捨入與最低手續費規則。

### 3.3 長期演進與多資產完整性（C 7.6 · B 6.8 · A 6.0）

**C 是唯一端到端設計出從自用到多使用者產品之路徑的提案：**

- 租戶、權限授予（entitlement）與 OIDC/WebAuthn；
- 作為單一寫入者的訂單閘道；
- 由客戶自行託管、用於個人台灣憑證的邊緣連接器；
- 最廣的台灣涵蓋範圍，包括用於新台幣加密貨幣的 MAX 與 BitoPro；
- 最完整的授權與監管模型。

然而，它低估了轉接器的成本（它說使用 Nautilus 轉接器，卻透過自家的交易場所閘道路由訂單），而且其 `Bond` 型別沒有指定進入回測器的路徑。

**B 擁有最完整的商品模型**，對需要散布的產品而言授權狀態也最乾淨（不隨附任何 LGPL），但它重新實作了每一個轉接器，而且沒有租戶機制。

**A 是目前在台灣最可執行的方案，**但其接縫很薄弱。策略與 Nautilus API 耦合，也沒有租戶或訂單閘道契約。它聲稱日後的服務會是「一項授權專案而非重寫」，這與其自身的觸發條件表相矛盾。

**建議：** 先建構 A 的範圍，並從第一天起採用 C 的低成本接縫，再加上 B 的能力旗標、`Bond` 領域型別，以及「可散布物不含 LGPL」的規則。

## 4. 融合決策

### 4.1 主幹

**提案 A** 為主幹。它的平均分數最高，是唯一在可能的起始情境下沒有致命缺陷的提案，且其缺點可透過嫁接與縮減範圍來修正；而 B 與 C 的缺點對小團隊而言是結構性的。B 與 C 成為**帶有明確觸發條件的演進路徑**（見[主報告](../README.zh-TW.md)中的 T1–T11）。

## 7. 帶入 Phase 0 的待驗證事項

這些項目尚未驗證，或取決於只有探索性實作才能揭示的行為。每一項都會產出一份 ADR，或更新既有的 ADR。

1. NautilusTrader v2 樹外（out-of-tree）轉接器 API 的成熟度（用於 Shioaji 轉接器）。
2. 台灣集合競價、漲跌停鎖死時拒絕成交、瞬間價格穩定措施（volatility interruption）與零股委託簿，能否以 Nautilus 成交/撮合擴充來表達（否則觸發 T7）。
3. 在 `BacktestNode` 內處理公司行動現金與部位調整的 v2 機制。
4. 以 Valkey 作為 Nautilus 的 Redis 後端，以及外部串流的輸出格式。
5. IBKR 緊急停止開關的取消語意（`reqGlobalCancel` vs master client ID）；定期 2FA 重新驗證的頻率；第二個使用者名稱是否能取得獨立的連線階段。
6. 各實際交易之交易場所與商品對 dead-man 與斷線即取消（cancel-on-disconnect）的支援情況。
7. Shioaji：以極小額真實委託測試零股行為（模擬器會拒絕零股）、連線階段限制，以及從第二個連線階段取消委託的路徑。
8. TAIFEX 夜盤交易日規則。
