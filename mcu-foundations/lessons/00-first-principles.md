# 第一課 從程式流程理解 MCU

今天用 60 至 90 分鐘建立第一張心智模型，不需要開發板。讀完應該能解釋：為什麼程式有在跑，系統卻仍然會漏資料。

## MCU 比一般應用程式多負責什麼

一般應用程式常把硬體初始化與排程交給作業系統。MCU 韌體可能直接負責這些工作：選時脈、設定接腳、啟動周邊，再安排何時處理事件。即使加了 RTOS，也仍需理解硬體設定與時序。

GPIO 是可由程式控制的數位接腳功能；timer 是能依時脈計數並產生事件的硬體；UART 是常見的非同步序列通訊周邊。先把它們看成有設定、狀態、輸入與輸出的機器，不必先背 API。

## 從 reset 到可見結果

以下是典型、簡化的執行過程，具體順序依晶片和啟動碼而定。

```text
供電或 reset
    → 硬體開機流程或 boot ROM
    → 啟動碼建立 stack 與 C 執行環境
    → 必要的系統初始化
    → main
    → 設定周邊
    → 持續處理事件
```

C 執行環境的建立通常包括讓有初值的靜態資料出現在執行時記憶體，以及清零對應的未初始化靜態資料區。之後實作時要在啟動碼和 linker 配置中找證據，不要把這張圖當作所有晶片的精確時序。

## 一個會漏資料的設計

假設感測器每 10 ms 應讀取一次，LED 每 500 ms 切換一次。如果主迴圈先讀感測器，再用 busy wait 等待 500 ms，等待期間主迴圈不能處理下一次讀取。CPU 忙碌並不表示系統有在完成應做的工作。

改善方式是讓時間與工作分開：用時間來源判斷哪些工作到期，每次只做有限的工作就返回。之後再引入 timer 中斷、buffer 與 DMA；這些機制各解決不同問題，並不自動讓整個系統符合時間需求。

```text
重複執行：
    取得目前時間
    如果取樣到期：取得一筆資料，更新下次期限
    如果 LED 到期：切換 LED，更新下次期限
    處理有限數量的接收資料
    推進傳送狀態
```

如果「取得一筆資料」本身阻塞 50 ms，換成這種迴圈仍無法保證 10 ms 取樣。你還要量出工作時間、定義逾期策略，或讓硬體自主取樣。

## 動手計算資料預算

假設每秒 1,000 筆，每筆封包共 12 bytes；UART 使用 115,200 baud、8N1，且本例每個符號傳一個 bit。8N1 的每個 byte 需要起始位、8 個資料位與停止位，共 10 bits。

先自行回答，再看下方解析：

1. 每秒至少產生多少 bytes？
2. 理想狀況下 UART 每秒最多傳多少資料 bytes？
3. 1 KiB 的 buffer 能不能解決持續超載？
4. 若傳送完全停住 50 ms，至少需要多少空間容納這段期間的新資料？

### 解析

來源是 12,000 bytes/s，理想傳輸上限是 115,200 ÷ 10 = 11,520 bytes/s，因此持續超載。額外的封包間隔或軟體等待只會讓有效吞吐更低。

在連續平均速率模型中，積壓每秒增加 480 bytes；初始為空的 1,024-byte buffer 大約 2.13 秒就滿。真實滿載時間還受封包突發與初始佔用影響。增加 buffer 可以承受暫時停頓，無法修補長期的平均速率不足。

50 ms 內會產生 600 bytes，這只是新資料的容量需求；還要加上原有積壓、邊界時刻的封包與設計餘裕。可行的改善包括降低取樣率、縮短封包、提高連線速率或改介面，並重新檢查接收端能力。

## 有軟體經驗仍要補的 C 觀念

固定寬度整數、位元遮罩、指標、物件生命週期和對齊，都會直接影響韌體。Unsigned 整數運算有模數語意；一般 signed 整數溢位不能當作可靠的回繞機制。

`volatile` 常用於硬體暫存器存取，但它不提供原子性或完整的跨執行脈絡同步。主迴圈、中斷和 DMA 共用資料時，要另外設計所有權與同步；不能只加 `volatile` 就宣告問題解決。

先不用寫通用 driver framework。選一個 GPIO 操作，理解它從 C 程式到實體接腳的因果關係，就比一次記住十套 SDK 更有價值。
