# MCU 實作路線

每關依序做四件事：先預測結果，完成最小實作，量測實際結果，再故意製造一個可恢復的錯誤。初期可以用官方範例建立可運作基線，再縮小到自己能解釋的程式。

## 分階段驗收

| 階段 | 學習與實作 | 通過條件 |
| --- | --- | --- |
| 0 約 1 週 | 第一課；補 C 的指標、位元操作、整數寬度與儲存期 | 能畫出資料路徑，算出頻寬，說明 unsigned 溢位與 signed 溢位差異 |
| 1 約 1 至 2 週 | 建置、燒錄、斷點；讀 startup、linker script、map file | 從乾淨輸出目錄重建；斷在 main；找到全域變數地址與初始化來源 |
| 2 約 1 至 2 週 | GPIO、接腳複用、clock gate；讀 LED 電路；HAL 與暫存器對照 | 解釋 LED 為何可能低電位亮；從 API 追到硬體設定；不能只靠 delay 猜頻率 |
| 3 約 1 至 2 週 | timer、中斷、按鈕去彈跳、非阻塞狀態機 | 取樣排程與命令接收可同時前進；量測週期和抖動，說明 busy wait 的影響 |
| 4 約 2 週 | UART、環形緩衝區、I2C 或 SPI 感測器擇一 | 主機能辨識完整封包；拔除感測器或停止讀取時有 timeout 與明確錯誤 |
| 5 約 1 至 2 週 | ADC 與 DMA；批次處理、buffer 所有權 | 沒有適當 ADC 時先做 UART DMA；能說明誰可讀寫每個 buffer，量出超載與丟失 |
| 6 約 1 至 2 週 | 加入一種 RTOS；task、queue、mutex、ISR 邊界 | 對比加入前後延遲與記憶體用量；重現並修正一個競態；知道 ISR 可呼叫哪些 API |
| 7 約 1 週 | watchdog、重啟原因、設定儲存、休眠概念 | 注入卡死後可恢復；無效設定有預設值；不以無條件餵狗掩蓋故障 |
| 8 約 1 至 2 週 | 換平台移植相同資料採集器 | 主機端協定測試沿用；列出應用、BSP、driver、build 各層改動及原因 |

階段時間是安排參考，部分練習可合併。進階的 cache 與 DMA 一致性、無線、安全開機和更新流程，等實際平台需要時再展開。

## 同一專案逐步演進

第一版每 10 ms 產生一筆序號與模擬數值，採二進位封包經 UART 送給電腦。電腦檢查序號是否連續，並統計每秒收到的筆數。

第二版加入命令，讓電腦調整取樣週期。先把解析器寫成可以在桌機上測試的純邏輯，明確處理不完整、過長和錯誤封包。收資料與送資料不應因等待一個命令而互相卡住。

第三版以真實感測器取代模擬資料，再用中斷或 DMA 搬運。定義 buffer 滿時的策略：丟最新、丟最舊、降低來源速率或回報故障；選哪個取決於需求，不能默默覆寫。

第四版加入 RTOS，比較是否改善結構。task 的數量應由執行與等待需求決定，不要每個函式都包成 task。

最後移植到另一平台。先保留資料格式、狀態機和驗收工具，只替換硬體相關邊界；若不得不改大量應用邏輯，檢查是不是把廠商型別或 callback 行為滲入了應用。

## 每次實驗要留下的證據

- 程式版本、板子型號、晶片完整料號、工具鏈和 SDK 版本。
- 預期的頻率、延遲、資料率與記憶體需求。
- 實際量測方式與結果，包括量測期間和樣本數。
- 注入的故障、觀察結果，以及恢復方式。
- 一段自己的解釋：換到另一個平台時，哪些假設要重新驗證。

初期用 debugger 和 UART 即可開始；到了訊號時序再加入邏輯分析儀。主機收到 log 的時間包含傳輸和緩衝延遲，不能直接當作 MCU 的精確執行時間。量測功耗則需要合適的電流量測方法，也要排除板上其他元件的影響。
