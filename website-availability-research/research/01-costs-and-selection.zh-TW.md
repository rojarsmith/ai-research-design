# 網站維護與備援的成本和選型

[返回主研究](../README.zh-TW.md)。查核日期：2026-10-12。金額皆為 USD，未含稅、匯差、網域註冊、既有 A 費用、人力、監控與日誌保存。VPS 與工時範圍是規劃估算，並非供應商報價；官方價格與估算分開列示。

## 成本先按需要持續工作的能力分級

| 目標 | 額外設施 | 低流量規劃費用 | 主要成本來源 |
| --- | --- | --- | --- |
| 更新程式時顯示訊息 | A 的靜態檔案與 nginx 規則 | 月費增量接近 0 | 初次設定、測試與部署流程 |
| A 死亡時仍顯示自訂畫面 | 外部 HTTP 入口及已儲存的頁面 | 可在免費額度內，或每月數美元起 | 邊緣方案、程式維護、所有正常流量的計費 |
| 故障時 DNS 轉 B | 健康檢查 DNS 加 B | DNS 數美元加 B；示例約 10 至 14／月 | DNS、HTTPS 探測、B 主機或靜態託管 |
| 自建入口 C 轉 A 或 B | C 與 B | 以每台 5 至 15 預算估算，約 10 至 30／月起 | 主機、頻寬、TLS、修補及 C 單點 |
| B 永遠代理 A | B | 以 B 每月 5 至 15 預算估算 | B 承接全部網站流量和維運 |
| 完整有狀態備援 | B 的應用、資料與依賴 | 可由數十至數百／月起，規模變大可遠高於此 | 資料庫 HA、複寫、備援容量、跨區流量、人力 |

最後一列只是量級，無法只憑一台 VPS 估算。若正常服務要 8 GB RAM、500 GB 檔案與高寫入 DB，B 不能拿只夠放一張 HTML 的 1 GB VPS 來估價。

## 已核對的公開費率

### Route 53 DNS 與健康檢查

官方一般區域價格：前 25 個 hosted zone 每個每月 **0.50**；standard DNS queries 前 10 億次每百萬次 **0.40**。Non-AWS endpoint 基本 health check 每個每月 **0.75**；HTTPS、字串比對、快速間隔與延遲測量，各項選配功能每個檢查每月各加 **2.00**。VPS 不在 AWS 時不能套用特定 AWS endpoint 的免費 health check 條件。[Route 53 官方價格](https://aws.amazon.com/route53/pricing/)

DNS 請求數不同於網站 HTTP 請求數。訪客的 DNS 會被快取；降低 TTL 也可能提高權威 DNS 查詢數。應以實際 DNS 查詢與探測功能計算。

**算例假設：**一個 zone、一個檢查 A 的 Non-AWS health check、每月 100 萬次 standard DNS queries、B 主機預算 8／月。B 不掛在路由用健康檢查上，另由營運監控確認可用；因此 B 的監控服務費未計入。

| A 探測設定 | DNS 與 health check 小計 | 加 B 8／月後 |
| --- | --- | --- |
| 基本 HTTP | 0.50 + 0.40 + 0.75 = **1.65** | **9.65** |
| HTTPS | 1.65 + 2.00 = **3.65** | **11.65** |
| HTTPS 與字串比對 | 1.65 + 2.00 + 2.00 = **5.65** | **13.65** |

如果還加一個 B 的 HTTPS health check，額外增加 0.75 + 2.00 = 2.75／月。若 A 與 AAAA 需要不同端點檢查，也要重算。免費額度、折抵或特殊 Alias 查詢優惠不納入此例，以免低估一般外部 VPS 的費用。

B 可換成靜態託管，但 URL、DNS 記錄類型、自訂域名 HTTPS、所有路徑的 503、API JSON 與健康檢查必須能符合需求。**不能直接把 S3 website endpoint 當成支援自訂網域 HTTPS 的 B**；常見做法要另加 CDN，則需重新計算 CDN 與憑證配置。[S3 website endpoint 限制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteEndpoints.html)

### Cloudflare Workers

Free 方案列有每天 100,000 requests，每次 10 ms CPU 限制；Standard Paid 的基本訂閱為 **5／月**，含每月 1,000 萬 requests 與 3,000 萬 CPU ms。超出 requests 每百萬 **0.30**，CPU 每百萬 ms **0.02**。純靜態資產與執行 Worker 程式的請求計費不同；這裡採「每個網站請求均進入代理 Worker」來估算。[Workers 官方價格](https://developers.cloudflare.com/workers/platform/pricing/)

**算例假設：**每月 100 萬次請求、每次平均 2 ms CPU；共 200 萬 CPU ms，均落在上述含量內，Worker 訂閱為 5／月。這個 2 ms 是待量測的假設，不是效能保證。若故障時由 Worker 直接回內建 HTML，不需要額外 B VPS，仍要加 A 的既有費用與必要監控費。

不能只計算「故障當天」的請求：代理 Worker 若在正常路徑，每天的正常訪問也會執行。多張圖片、API、重試及資產載入會增加請求數。超過免費方案限制時的失敗或 bypass 行為要依路由設定驗證，不能以免費額度代替正式可用性目標。

### Cloudflare Load Balancing 與自訂錯誤頁

官方方案頁列 Load Balancing **5／月起**，這是起價，不能直接當成任意來源數、監控區域與流量下的最終費用。應依實際購買設定核對來源數、健康監控、查詢量、區域及超額費率；歷史介紹文章的額度也不能自動視為今天的合約。[Cloudflare 官方方案與加購](https://www.cloudflare.com/plans/)

若已有 A，加一台預算 8／月的 B，與 LB 5／月起，則這個規劃下限為 **13／月起**；若原本已經有 B，新增費用可主要是 LB。B 不必在 Cloudflare 自己的機房，但需要允許入口與探針連線。

Custom Errors 與 Load Balancing 是不同功能。Custom Errors 的官方功能表不包含 Free，採網站付費方案時要把該方案費一併算入；不應假設買 Workers 的 5／月就取得網站 Pro 的錯誤頁權限。[Custom Errors 方案差異](https://developers.cloudflare.com/rules/custom-errors/)

### 其他供應商與自建服務

CloudFront、其他 CDN、託管負載平衡器與 DNS 備援服務，都可以列入同一比較。費用模型可能是固定方案、請求量、傳輸量、每小時計費與額外功能的組合；先用預估用量算總價，再比價。此研究不以未指定區域與流量的單一數字替代報價。

nginx OSS 或 HAProxy 的軟體本身不需商業訂閱，但主機、備援入口、頻寬、修補與排障並非免費。NGINX Plus 的原生主動 health check 等能力依商業授權計價，不能把 nginx OSS 的零授權費套到 Plus 功能。[NGINX 健康檢查功能條件](https://docs.nginx.com/nginx/admin-guide/load-balancer/http-health-check/)

## 工程與維运工時估算

以下以熟悉 Linux、DNS、HTTPS 與自身應用程式的工程師估算；首次操作、新技術、審核流程或複雜網路會延長。工時不含購買決策、資料庫遷移與修復既有問題。

| 工作 | 初次規劃工時 | 後續要維護什麼 |
| --- | --- | --- |
| A 本地 HTML 與 JSON 維護頁 | 2 至 4 小時 | 部署旗標、错誤攔截、頁面文字與回復測試 |
| DNS failover 配 B 維護頁 | 4 至 8 小時 | A/B 憑證、探測、TTL、IPv6、DNS 與監控 |
| 託管 HTTP LB 配 A/B | 4 至 12 小時 | pool 順序、探針、TLS、affinity、快取與事件警示 |
| Worker 直接生成維護回應 | 4 至 12 小時 | 程式、逾時、路由、額度、API 相容與平台更新 |
| B 代理 A 並在本機退回 | 4 至 8 小時 | B OS、入口安全、正常流量頻寬與跨機 HTTPS |
| 自建 C nginx 或 HAProxy | 8 至 16 小時 | C 的可用性、安全、TLS、健康檢查與觀測 |
| 浮動 IP 與外部控制器 | 1 至 3 工作日 | API 權限、競態、接管與回切、網路及單一擁有者 |
| 完整有狀態 A/B 備援 | 數日至數週以上 | DB、session、檔案、queue、fencing、回補及實戰演練 |

每季排一次受控演練，比只看「有備份、有 B」更能驗證能力。可視風險縮小或增加頻率，不能把上述工時當作通過演練的證明。

## 延遲與可用性不能只用月費比較

估算使用者受影響時間時，至少分出：**偵測故障時間、入口政策更新時間、DNS 或頁面快取等待、來源連線逾時、客戶端重試時間、資料恢復時間**。這些因素可能重疊，不是所有產品都單純相加。

| 機制 | 延遲主要受什麼影響 | 對你的回切需求 |
| --- | --- | --- |
| 同機 nginx 靜態頁 | 該請求連線或回應逾時 | 程式恢復即可，但不保護 A 整機 |
| 每次先試 A 的外部代理 | 每次對 A 的逾時，健康狀態及快取 | 不會永久黏在 B，但 A 壞著時每次試 A 可能拖慢 |
| 主動健康檢查 LB | 探測週期、門檻、跨區健康聚合 | 可持續探測 A，再讓新流量回 A |
| DNS failover | 外部探測加 DNS 快取與客戶端連線 | 可最終回 A，難保證立即全面切回 |
| IP 搬移 | 探測、API、網路收斂與連線重建 | 同一 IP，可快切；依供應商範圍與 API 可用性 |

若自訂探針每 10 秒一次、3 次失敗，僅名義探測區間就約 20 至 30 秒，再加逾時及健康聚合；這是簡化算例，不是任何產品 SLA。CloudFront 官方原生 origin failover 預設最多嘗試建立連線 3 次、每次 10 秒；若未調整，單個 cache miss 可能花到 30 秒才嘗試 B，不能僅因為是 CDN 就預期立刻切換。[CloudFront 逾時與嘗試次數](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/high_availability_origin_failover.html)

RTO 是恢復可用服務的目標時間；RPO 是可容許遺失的資料時間範圍。B 只顯示維護頁時，改善的是訊息可達性，並沒有使原業務 RTO 歸零，也沒有提高 A 上資料的 RPO。

## 選型建議

| 你最在意的條件 | 優先方案 | 接受的取捨 |
| --- | --- | --- |
| 幾乎零額外月費，主要處理部署與程式故障 | A nginx 本地維護頁 | A 整台死掉仍無畫面 |
| A 整台壞了也有畫面，不想維護 B | 外部邊緣直接回頁面或 CDN 已存的錯誤頁 | 平台額度、方案費與自行程式成本 |
| 最低成本跨 VPS 供應商備援，可以等待 DNS 更新 | 健康檢查 DNS 加 B | 快取更新與客戶端重試，回切也是逐步完成 |
| 同一網址，A 故障走 B，恢復時新請求優先回 A | 外部 HTTP 主備 LB | 每月服務費與入口依賴；取消不必要的 affinity |
| 僅 A、B 兩台且自己會管理 nginx | B 永遠代理 A，故障回本地頁 | B 成為入口單點、承擔所有正常流量 |
| 同一供應商且有可搬移 IP | 浮動 IP 加可靠外部控制 | 供應商網路範圍、API、接管競態 |
| 下單、付款、寫入服務不中斷 | 完整服務備援加資料 HA | 明顯更高的工程與營運成本 |

此情境沒有一種方案同時保證「免費、零額外入口、A 整台故障仍有畫面、所有人立即切回、資料完全不中斷」。先選需要保護的故障範圍和 B 的能力，再決定價格與維運負擔。
