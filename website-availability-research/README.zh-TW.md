# 網站維護畫面與 VPS 故障切換研究

研究日期：2026-10-12，Asia/Taipei。範圍涵蓋網站、HTTP API、網路服務前端與 nginx VPS；以現有主機 A 為主要服務、遠端主機 B 為備援的需求為中心。

**可以做到平常走 A、A 故障走 B、A 恢復後再走 A，但整台 A 故障時，切換決策必須位於 A 之外。** A 上的 nginx 可以在應用程式故障時顯示維護頁，無法在自身主機斷電或失聯時接收請求並導流。若希望維持同一網址，通常選外部代理或負載平衡器；若容許部分訪客等待 DNS 快取更新，DNS failover 是成本較低的選項。

B 的角色決定大部分成本。B 只供應一張維護頁，不需要同步使用者資料；B 若要繼續提供完整服務，就必須處理資料庫、登入 session、檔案、背景工作及切回時的資料一致性。買兩台 VPS 並不自動得到完整高可用服務。

## 先分清楚故障發生在哪一層

使用者取得畫面的路徑通常是：DNS 查詢 → 對外 IP → TCP 連線 → TLS 握手 → HTTP 入口 → 應用程式 → 資料庫等依賴。能回答 HTTP 的元件必須位於故障元件之前，且仍然存活。

| 故障或維護情境 | A 上的 nginx 能否顯示維護頁 | 要增加什麼 |
| --- | --- | --- |
| 計畫更新應用程式，A 與 nginx 正常 | 可以 | 維護旗標、靜態 HTML、503 回應 |
| 應用程式未啟動、連線被拒絕或回應逾時 | 可以，前提是 nginx 有足夠資源 | 攔截上游錯誤、設定逾時與錯誤頁 |
| 資料庫故障，應用程式明確回傳 503 | 可以 | 有意義的 readiness 檢查與 API 錯誤處理 |
| 應用程式回傳 200，但頁面內容其實壞了 | 一般錯誤碼攔截無法辨識 | 特定內容檢查、功能探針或應用程式改善 |
| nginx 本身停止或設定失敗 | 不可以 | 外部 HTTP 入口或 DNS 備援 |
| VPS 斷電、OS 當機、整台 OOM 或網路中斷 | 不能可靠提供 | 外部代理、DNS failover、供應商浮動 IP 等 |
| 訪客到 A 的 TLS 握手失敗或憑證無效 | 瀏覽器通常在 HTTP 之前就阻擋 | 對外 TLS 由可用的外部入口終止，或修復憑證 |
| 網域無法解析、註冊到期或 DNSSEC 設定錯誤 | 不可以 | DNS 與網域層修復，另用已知獨立狀態網址溝通 |
| 訪客自身斷網 | 伺服器無法傳送新畫面 | 已安裝的離線前端或 service worker；首次訪客仍無法取得 |

「A 活著」不足以表示服務可用：只檢查 ping 或 port 443，可能漏掉資料庫故障、登入失效或程式死鎖。另一方面，所有功能都塞入同一個健康檢查，又可能因非核心依賴失效而讓整站退出服務。應依網站必要能力定義健康條件。

## 維護訊息該怎麼呈現

### 計畫維護與突發故障使用不同文字

計畫維護可寫「系統升級中，預計 14:30 恢復，期間暫停登入與提交」。只有確定時程才寫預計恢復時間，並標示時區。突發故障宜寫「服務暫時無法使用，我們正在處理，請稍後重試」，附最後更新時間或獨立狀態頁；不要把未知故障描述成正在升級，也不要承諾沒有依據的「幾分鐘後恢復」。

部分功能受影響時，在仍可使用的介面顯示橫幅或停用相關操作即可。例如付款暫停但商品瀏覽正常，不必讓全部網址都變成維護頁。桌面或手機軟體應將網路錯誤轉成介面訊息，保留未送出的內容，明確說明提交結果是否未知。

### HTTP 狀態與快取會影響實際恢復

暫時無法提供原服務時，HTML 或 API 通常回傳 **503 Service Unavailable**，並可附 `Retry-After: 60`，表示建議稍後再試，不是保證 60 秒後恢復。`Retry-After` 不會讓一般瀏覽器自動重新整理。[HTTP 語意標準](https://www.rfc-editor.org/rfc/rfc9110.html)

維護回應採 `Cache-Control: no-store`，同時確認 CDN 對錯誤碼的快取規則；某些 CDN 的錯誤快取另有設定。不要將所有網址的維護內容改成可長期快取的 200，否則監控會誤判正常，搜尋引擎也可能把維護文字當成真正頁面。短暫全站停用可以使用 503，長時間全站持續 503 仍可能影響收錄。[Google 暫停網站指南](https://developers.google.com/search/docs/crawling-indexing/pause-online-business)、[CloudFront 錯誤快取](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/custom-error-pages-expiration.html)

API 應回 JSON 錯誤，不要讓 `/api/orders` 得到 HTML，導致客戶端出現 JSON 解析失敗。CORS、認證錯誤和維護錯誤也要分開；跨來源前端若拿不到正確的 CORS 標頭，可能只看得到通用網路錯誤。

維護頁本身應使用本地或邊緣儲存的 CSS、圖片與字型；最好是一份自給自足的小型 HTML。若頁面依賴 A 的 JavaScript、API、資料庫或外部登入才能顯示，A 故障時它也會壞。獨立狀態頁不依賴 A，可保留服務範圍、事件時間線與更新資訊；DNS 全面故障時，使用者仍需知道它的另一個網址。

### 非 HTTP 服務與軟體本體當機

SSH、資料庫連線、MQTT 或自訂 TCP／UDP 服務不能以回傳 HTML 直接代替原協定。可用對應的外部網路入口或 DNS 機制切換服務，但「維護中」的畫面須由仍在執行的客戶端依連線失敗或協定錯誤顯示，並另提供 HTTP 狀態頁。客戶端不理解的文字只會變成協定錯誤。

手機或桌面程式仍在執行、只有遠端服務不可用時，可以顯示維護訊息並保留本地草稿；程式本體已經崩潰退出時，它自己無法再畫出維護畫面，需要獨立啟動器、更新程式、監督程序或作業系統的錯誤介面。尚未下載前端的首次網站訪客，也無法依靠同一個已失聯主機傳來的 JavaScript 顯示訊息。

## 實務做法與能力邊界

| 做法 | 應用程式故障 | A 整台故障 | 自動回到 A | 優勢 | 主要限制 |
| --- | --- | --- | --- | --- | --- |
| 應用程式維護模式 | 程式仍能執行時可以 | 不可以 | 關閉模式即可 | 易配合登入、功能權限與維護時間 | 程式自己壞了就無法顯示 |
| A 上 nginx 靜態維護頁 | 可以 | 不可以 | 應用恢復或移除旗標 | 幾乎無額外月費、不依賴程式 | 同一台主機仍是單點 |
| A 的 nginx 備援上游 B | 可以 | 不可以 | 被動重試恢復後可回 A 的程式 | 同一網址、nginx OSS 可實作 | nginx 在 A 上，A 死掉就失去入口 |
| 外部 CDN 自訂錯誤頁 | 視攔截碼與功能而定 | 可以，在入口仍正常時 | 新回源成功且錯誤快取過期後 | 不必維護完整 B，頁面可存在 CDN | 方案與錯誤種類限制；不是完整服務備援 |
| 外部 Worker 或邊緣程式 | 可以自行定義 | 可以，在邊緣正常時 | 每次先試 A，或依健康狀態回切 | 可分 HTML、API、維護時段 | 要自行寫逾時、狀態、資安與測試；平台額度與限制 |
| 外部 HTTP 負載平衡器 | 可以，健康探針需涵蓋程式 | 可以 | 設定 primary 與 backup 及回切政策 | 同一入口、主動探測、來源切換不依賴訪客 DNS 更新 | 增加服務費或入口主機；入口本身也需要高可用 |
| 健康檢查型 DNS failover | 可以，檢查需涵蓋程式 | 可以 | DNS 新回答回 A | 不讓網站流量經過第三方代理，跨供應商可用 | DNS 快取、連線與 IPv4／IPv6 分歧，無法立即全面切回 |
| 外部監控呼叫 DNS API 改記錄 | 視監控而定 | 可以 | 控制器再次改回 A | 可沿用 DNS 供應商、政策自由 | 自行維護狀態機、API 權限、競態與故障恢復 |
| 供應商浮動 IP 或 VRRP | 視探針而定 | 在支援的網路範圍內可以 | 可設優先權與延遲回切 | 同一 IP、無 DNS TTL 等待 | IP 可搬移範圍、網路與供應商限制；不能任意跨網際網路 |
| CDN 過期內容或離線前端 | 只涵蓋已快取內容 | 部分可以 | 快取更新或客戶端重連 | 展示頁可能持續可讀 | 不能保持動態功能、首次訪客或寫入服務 |
| 藍綠部署與滾動更新 | 可減少計畫中斷 | 單台配置仍無法承受 A 故障 | 部署完成切到新版本 | 很多升級根本不必顯示全站維護頁 | 資料庫 migration、容量與版本相容性要規劃 |

### nginx 的備援功能保護的是上游

nginx OSS 可用 `backup`、`max_fails`、`fail_timeout` 決定何時改送備援上游；這些條件是觀察實際請求的被動機制，並不等於主動定時呼叫 `/readyz`。原生主動 HTTP health check 屬於 NGINX Plus 功能；開源 HAProxy 則有主動健康檢查，可用於獨立入口。[nginx 上游設定](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)、[NGINX 健康檢查功能](https://docs.nginx.com/nginx/admin-guide/load-balancer/http-health-check/)、[HAProxy 健康檢查](https://www.haproxy.com/documentation/haproxy-configuration-tutorials/reliability/health-checks/)

如果只有一個上游，不能期待 `max_fails` 幫你找出另一台；靜態維護頁應以錯誤處理完成。範例的 `error_page` 是把錯誤轉成靜態訊息，`backup` 是改送另一個上游，兩者是不同工具。

### CDN 自訂錯誤頁與備援主機不是同一功能

邊緣已經接到訪客請求，所以可以在回源失敗時回答頁面。若頁面預先存放在邊緣，顯示它不需要臨時向已失聯的 A 下載。

不能假設只開啟 Cloudflare 免費代理就會自動改走 B 或出現自己的品牌維護頁。其官方 Custom Errors 表列 Free 不支援、付費方案可用；不同類型錯誤頁仍有方案差異。Workers 與 Load Balancing 是另行配置的能力，帳單與網站 Pro 方案也不同。[Cloudflare Custom Errors 功能表](https://developers.cloudflare.com/rules/custom-errors/)

CloudFront 可設 A 為 primary、B 為 secondary，回源請求先嘗試 A，失敗才嘗試 B；其原生 origin failover 只支援 `GET`、`HEAD`、`OPTIONS`，不能將一般交易 API 的 `POST`、`PUT` 當成同樣受到保護。命中快取時不會回源，維護內容若被快取會延後回到正常畫面。[CloudFront origin failover](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/high_availability_origin_failover.html)

### 健康檢查型 DNS 與輪詢 DNS 有明顯差別

同時公布 A 與 B 的兩個普通 DNS A 記錄，通常只是讓客戶端取得多個位址，不表示 DNS 知道誰故障，也不表示 A 是優先、B 是備用。無法拿它保證你的主備需求。

DNS failover 的健康狀態由外部服務維護。以 Route 53 為例，primary 健康時回 primary，不健康時依 secondary 的健康及設定決定回答；兩端都不健康時仍有既定回答政策，不會憑空產生第三個可用站點。[Route 53 健康與回答政策](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-how-route-53-chooses-records.html)

較低 TTL 只降低正常遵守 TTL 的快取等待；解析器、作業系統、瀏覽器、HTTP 連線與客戶端重試策略仍會影響行為。60 秒 TTL 不等於 60 秒內全世界都切完，更不會搬走已經建立的 TCP 或 WebSocket 連線。

## A 主機與 B 主機的具體解法

### 方案一 A 上 nginx 顯示維護頁

```text
訪客 → A 的 nginx → A 的應用程式
                 └→ 本機靜態維護頁
```

適用於部署、程式重啟或上游故障。在 nginx 設定 `proxy_intercept_errors` 和指定錯誤頁，把 502、503、504 轉為 503 維護訊息；維護旗標可在更新前主動阻擋新請求。[nginx proxy 設定](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)、[nginx error_page](https://nginx.org/en/docs/http/ngx_http_core_module.html#error_page)

這一層值得先做，成本低，能讓一般更新更清楚。但是它只覆蓋 A 仍能服務 HTTP 的情況。

### 方案二 外部代理在前面 A 與 B 在後面

```text
                         ┌→ A：正常網站，第一優先
訪客 → 外部 HTTP 入口 E ──┤
                         └→ B：維護頁或完整備援，第二優先
```

E 可以是託管負載平衡器、CDN 搭配負載平衡服務、Worker，或自己維護的獨立 nginx／HAProxy 主機 C。DNS 從一開始就指向 E；E 探測 A，故障後送 B，A 通過恢復條件後重新送 A。因為 E 還活著，不需要 A 自己導流，也不必把瀏覽器網址改成 B 的網域。

針對維護頁，B 準備所有路徑的 HTML 與 API 503 回應即可；E 的健康監控可以探測 B 的 `/readyz`，這個特定端點回 200，代表「B 已準備好回答維護訊息」。B 的一般網址仍回 503，不能讓監控直接探測其 503 首頁而誤認 B 也壞了。

Cloudflare Load Balancing 的 `Off — Failover` 政策可依池順序先 A、再 B。官方文件明示 primary 恢復後會自動回切，但 session affinity 等設定可能讓後續請求繼续留在 B。你的需求應取消不必要的黏著設定，並以新請求驗證切回。[Cloudflare 主備與切回政策](https://developers.cloudflare.com/load-balancing/understand-basics/traffic-steering/steering-policies/standard-options/)

若只有一台自建 E，E 會成為新單點。這仍能隔離 A 的故障，卻不能聲稱消除了所有入口故障；高可用 E 需要兩個入口加供應商網路支援，或採託管服務。託管入口也有其自身的服務、設定及供應商故障範圍。

### 方案三 讓 B 永遠當入口 正常時代理到 A

```text
訪客 → B 的 nginx → A 的正常網站
                └→ B 本機維護頁
```

這是只使用 A、B 兩台 VPS 的實用變體。DNS 固定指向 B，B 正常時代理到 A；A 壞了，B 在本機回答維護頁，A 恢復後下一批正常請求又代理到 A。內容服務仍在 A，入口一直在 B；如果你要求「連入口流量平常也必須直接到 A」，這個方案不符合該條件。

B 要承擔全部流量、TLS 與轉送頻寬，不是只在故障時收流量。A 與 B 跨區時，每個正常請求也增加一段網路延遲。B 自己失聯則網站同樣無法訪問，且將 B 維護時的風險帶進主站。適合可接受這種單點轉移、希望少買一台 C 的情況。

### 方案四 DNS 健康檢查直接切 A 與 B

```text
外部 DNS 服務：持續檢查 A 的服務健康
  健康 → 查詢回答 A 的 IP
  故障 → 新查詢回答 B 的 IP
  恢復 → 新查詢再次回答 A 的 IP

訪客 → 快取的 DNS 位址 → A 或 B
```

配置同一服務網域的 primary 與 secondary 記錄，A 與 B 都準備該網域的有效 HTTPS 憑證。監測 A 的固定來源位址與正確 Host，不要透過會切去 B 的公用網域查健康，否則可能監到 B 而誤以為 A 恢復。

A 恢復後，權威 DNS 可以自動改回 A，但曾快取 B 的訪客可能短暫繼续使用 B；若 B 當時是維護頁，就會稍後才能回到主站。因此這個方案符合「最終自動回到 A」，不能嚴格滿足「A 恢復那一瞬間所有人立刻停止用 B」。

IPv4 A 記錄與 IPv6 AAAA 記錄必須一起處理；若只有 IPv4 切 B，但 AAAA 還指向失聯 A，一部分訪客仍可能失敗。避免使用長時間快取的永久 HTTP 重新導向代替主備路由。

### 方案五 供應商浮動 IP 或受支援的 VRRP

```text
訪客 → 同一對外 IP → 目前持有 IP 的 A 或 B
                    ↑
          外部控制器或受支援的高可用網路切換
```

若 VPS 供應商允許把一個對外 IP 重新指派給另一台主機，可由仍存活的 B 或外部控制器執行 API 搬移；恢復後依政策搬回 A。須處理「只是兩台彼此看不見」與「A 真的失聯」的差別，確保同一時間只有一方接管。

Keepalived／VRRP 不是讓兩台任意遠端 VPS 共用網際網路 IP 的魔法。兩台主機自行加同一個 IP，不會使上游路由自動改變；仍須供應商支援的網路、位址轉送或 API。以 Hetzner 為例，Floating IP 可跨其部分機房，但仍必須在同一 network zone，不能據此推論可跨任意供應商。[Hetzner Floating IP 範圍](https://docs.hetzner.com/cloud/floating-ips/faq/)

IP 改派也不會遷移已建立的連線或程式記憶體。若 B 提供完整服務，資料問題照樣存在。

## B 只顯示頁面與 B 繼續提供服務

| B 的能力 | 使用者能做什麼 | 必要準備 | 切回難度 |
| --- | --- | --- | --- |
| 靜態維護頁 | 得知服務暫停、看狀態、稍後重試 | 頁面、TLS、API 503、獨立入口 | 低，不產生需要合併的業務資料 |
| 唯讀備援 | 看已同步內容，部分歷史資料 | 唯讀資料副本、過期時間、禁用所有寫入及背景寫入 | 中，需辨識資料是否過期與 session 問題 |
| 完整應用程式與同一外部資料庫 | 登入及正常業務，視依賴可用性 | 版本、session、檔案與任務協調；資料庫本身高可用 | 高，外部共享資料庫仍可能是共通單點 |
| 完整應用程式與可晉升的資料副本 | A 故障時接管讀寫 | 複寫、fencing、單一寫入者、資料回補、切回程序 | 很高，不能 A 開機後直接把流量切回舊資料 |
| 多區或多供應商持續服務 | 視設計承受機房或供應商故障 | 一致性、網路、容量、跨區費用與持續演練 | 很高，適合有明確可用性目標及維運資源的服務 |

完整備援還要考慮：Cookie 簽章金鑰與 session 儲存、上傳檔案、寄信／付款／webhook 的重複執行、排程與 queue worker 的唯一執行者、第三方 IP 白名單、秘密與憑證、DB schema 相容性。只同步程式碼或只做每日備份並不足夠。

若 B 接受了寫入而 A 還有舊資料，A 恢復通電並不是回切條件。必須先決定誰是資料權威、阻止舊主繼續寫入、完成複寫與資料核對，再讓 A 通過 readiness。這是你的「恢復後走 A」需求在完整服務情境中最重要的能力邊界。

## 自動切回要如何定義

以下為建議政策，不是各供應商的預設值。實際可用的探測間隔、失敗門檻、成功門檻與延遲回切，依產品與付費方案確認；無內建延遲功能時可透過 readiness 條件或外部控制器實作。

1. A 檢查失敗達門檻，例如連續 3 次失敗，轉至 B。探針不能靠 A 上的排程執行。
2. 故障期間仍直接探測 A，並持續確認 B 能提供預定的維護或備援能力。
3. A 恢復後先通過程式、必要依賴、版本及資料角色檢查；例如連續 5 次成功，再穩定觀察 60 至 180 秒。
4. 維護旗標仍存在時不回切。此旗標代表操作人員尚未放行，即使 port 已開也不算可用。
5. 放行後讓新請求回 A；WebSocket、SSE、正在下載的內容及已有 TCP 連線不會自動搬移。依產品決定自然排空或通知客戶端重連。
6. B 是完整有狀態服務時，先完成資料回補與單一寫入者切換，不能只看 HTTP 200。

這樣可以減少 A 不穩定時反覆切換的抖動。若「不能繼續走 B」意指新請求不得再黏著 B，需取消 session affinity、檢查快取及 DNS 更新；若包含所有既有連線，則還需要主動結束 B 的連線，且使用者可能遇到一次中斷。

## 容易看起來有備援 實際卻無法達成的做法

- **A 的程式偵測自己整台死亡後再改 DNS。** 主機死了就無法執行，監控與切換必須外移。
- **A 回 302 到 B，就以為能處理 A 整台故障。** 重導向也要 A 先收到請求。直接把使用者送往 B 的網域，回到 A 還需要額外動作。
- **備援 HTML 放在 A，外部入口故障時才去下載。** 頁面必須預先存到仍活著的元件。
- **A 恢復了卻永遠走 B。** 常見原因包含 DNS 快取、黏著 session、B 回 301／308、維護頁快取、維護鎖未解除或 primary 優先權未設定。
- **檢查公用首頁，而它在故障時仍回 200 維護頁。** 監控永遠認為健康，失去切換條件。
- **把付款、訂單等 POST 逾時後自動重送 B。** A 可能已完成寫入但回應丟失；必須用冪等鍵與結果查詢協定處理，不能讓入口任意重播。
- **以 CDN 的舊內容快取當作完整可用性。** 登入、即時查詢與寫入通常仍依賴故障來源，還可能有個資快取風險。
- **A 與 B 同一機房、共用同一 DB，卻宣稱能承受所有災害。** 冗餘只能抵抗已隔離的故障範圍。

## 依目前需求的選擇

如果目標是「A 故障時，使用者至少看得到清楚訊息」，先加 A 的 nginx 本地 503 頁，再選一個 A 外的入口。偏向少維運，可用託管 HTTP 入口配靜態維護回應；希望費用低且能容忍數分鐘內逐步切換，可用健康檢查型 DNS 配 B；只想維護兩台 VPS 且接受 B 入口單點，可把 B 永遠放前面代理 A。

如果目標是「A 故障期間，B 仍繼續承接完整業務」，先規劃資料與任務接管，再選流量入口。入口切換通常比資料安全切回容易，不能讓資料架構被主備 nginx 設定掩蓋。

若希望計畫升級也盡量不中斷，則加做藍綠或滾動部署、連線排空與相容的資料庫變更；維護頁保留為必要的退路。

針對你現有的 A nginx：**可以先做軟體層維護頁；要涵蓋 A 整台故障並自動回 A，優先評估外部 HTTP 主備入口，其次評估 DNS failover。** 精確費用與步驟見[成本與選型](research/01-costs-and-selection.zh-TW.md)及[實作與驗收](research/02-implementation-and-validation.zh-TW.md)。
