# MCU HMI 架構與共同評測方法

[回主報告](../README.zh-TW.md) · 日期：2026 年 10 月 12 日。

不同產品先按架構選型，再以共同任務測量可交付結果。以下計算是明示假設的工程估算；評測流程是後續可執行的方法，沒有宣稱已取得實測結果。

## 三種系統架構

### 主 MCU 執行圖形框架

主 MCU 同時處理 UI、產品控制與通訊；工具產生的 UI 程式進入韌體建置。LVGL 配合 SquareLine，以及 STM32 配合 TouchGFX 都屬此路線。採 AT32 時，可從官方 LVGL 範例開始，但仍要驗證版本及自己的板級配置。[SquareLine 工作流程](https://docs.squareline.io/docs/introduction/typical_dev/)、[TouchGFX 組成](https://support.touchgfx.com/docs/introduction/what-is-touchgfx)、[AT32 範例](https://arterychip.com/download/Example%20Code/SC0118_LVGL_FreeRTOS_Demo_on_AT32_EN_V2.0.0.pdf)。

工程判斷：此架構便於共享資料與除錯，也讓 UI 與控制任務競爭 CPU、RAM、DMA 及記憶體頻寬。若操作延遲或控制週期有要求，應測量圖形負載增加時的排程，而非只看單獨 UI demo 的 FPS。

### 主控交換資料與智慧顯示端渲染

主控傳遞數值、狀態及操作結果，顯示端保留圖片、字型與畫面資源。DWIN DGUS 和 Levetop 串口屏控制晶片是代表；兩者是否適合特定主控，取決於控制方式、模組或晶片及通訊細節。[DWIN 文件](https://www.dwin-global.com/development-guide/)、[LT268B／LT269](https://www.levetop.cn/tw/Product/info.aspx?itemid=592&lcid=131)。

工程判斷：可以降低既有主控的圖形工作，但增加跨裝置狀態同步。需要測試掉線提示、重連、封包解析、觸摸事件回報，以及主控／UI 版本不一致時的行為。串口屏是資料交換架構，通常不適合把主控當成全畫面像素串流來源。

### CAN 網路上的整合顯示模組

華凌 CAN 系列把顯示、MCU、CAN 與 GUI Builder 整合，分為 CANopen 與自訂 CAN ID 路線。若改用客製韌體，必須重新確認 GUI 工具與通訊堆疊的支援責任。[華凌 CAN 系列](https://www.winstar.com.tw/zh-tw/products/smart-display/can-display.html)。

工程判斷：適合已有 CAN 資料模型的設備，但訊號映射、端序、比例、單位與逾時行為仍是產品規格。CANopen 有物件字典不代表每個客戶網路可直接接上；DBC 匯入也不代表 bus load、訊息週期與失效處理已完成設計。

HMI Studio 的公開定位包含視覺、邏輯及協定編輯，但目前不足以把它固定歸入上述某個硬體架構。評測前要先取得目標裝置與執行環境說明。[產品頁](https://www.hmistudio.io/)。

## 記憶體與頻寬計算

### Framebuffer

假設 RGB565、每 pixel 2 bytes，且配置完整單一 framebuffer：

`容量 bytes = 寬 × 高 × 2`

| 解析度 | 單 framebuffer | 雙 framebuffer |
| --- | --- | --- |
| 320×240 | 153,600 bytes，150 KiB | 300 KiB |
| 480×272 | 261,120 bytes，255 KiB | 510 KiB |
| 800×480 | 768,000 bytes，750 KiB | 1,500 KiB |
| 1024×600 | 1,228,800 bytes，1,200 KiB | 2,400 KiB |

這些數字不包含 UI 物件、heap、stack、字型、圖像解碼、RTOS、通訊 buffer 及產品功能。1 KiB = 1,024 bytes。若採 ARGB8888，同樣解析度的 framebuffer 容量為表中兩倍。

部分更新或行緩衝可以減少 MCU 的 draw buffer；顯示控制器、面板或其他位置仍需承擔畫面儲存及輸出。LVGL 官方需求也分別列靜態 RAM、stack、heap、display buffer 與 framebuffer，不能把最小 heap 當成完整 HMI RAM 需求。[LVGL Requirements](https://lvgl.io/docs/open/introduction/requirements)。

### SPI 像素傳輸

假設 SPI 40 Mbit/s、RGB565、每次完整傳輸，且暫不計指令、間隙與渲染：

| 解析度 | 一幀傳輸理論下限 | 僅由傳輸推算的理論上限 |
| --- | --- | --- |
| 320×240 | 30.72 ms | 約 32.6 frames/s |
| 480×272 | 52.224 ms | 約 19.1 frames/s |
| 800×480 | 153.6 ms | 約 6.5 frames/s |

這是特定假設下的理想傳輸界線，不是任何產品的 FPS。局部更新可能大幅減少傳輸量；實際 SPI 時脈、指令 overhead、讀取資產、CPU 渲染與 DMA 重疊方式會改變結果。不同顯示介面不能只用 CPU 主頻比較。

### UART 資料交換

假設 UART 115,200 baud、8N1，每 byte 包含 1 start、8 data、1 stop bit，理想資料率為 11,520 bytes/s。若傳 480×272 RGB565 全幀，僅傳輸即需約 22.67 秒；若每 100 ms 傳送一個 40-byte 封包，單向約 400 bytes/s，佔此理想容量約 3.47%。

因此智慧屏應優先交換變數、事件及必要命令。上例不是 DWIN 或 Levetop 的實際協定占用量，也未計回覆、重試、輪詢及突發事件。

## 總成本模型

`總成本 = 工具與授權 + 一次性工程 + 數量 × 單台完整 BOM + 測試與認證 + 維護與供貨風險成本`

| 成本項 | 自建 MCU 與框架 | 專用串口屏晶片 | 整合智慧顯示模組 |
| --- | --- | --- | --- |
| 開發工具 | 框架、editor、IDE、debugger | Editor、compiler、燒錄器與配套韌體 | GUI Builder、客製工具與服務 |
| 硬體 | MCU、記憶體、LCD、觸控、PCB、電源等 | 控制晶片、Flash、LCD、觸控、PCB等 | 模組加接線、主控介面與機構 |
| 一次性工程 | BSP、顯示／觸控驅動、UI、通訊及效能 | 顯示板設計、資產製作、主控協定 | 模組整合、映射、機構及客製 |
| 維護 | 重建工具鏈、移植與元件升版 | 工具／韌體相容性及資源下載 | SKU、PCN、交期與替代模組 |

比較單台 MCU 售價和整片智慧顯示器售價會漏掉硬體與工程差異。量產數量很大時，較高的一次性工程可能有機會攤薄；少量或短交期時，整合模組可能降低總投入，須以實際報價及工時計算。

AI 工具的成本應另記為「模型用量、重試、人工修正與本機運算硬體」。免費評估版與開源框架也應計入整合及維護。

## 共同工作負載

先用可取得的 480×272 目標做基準；遇到硬體系列限制時，另立對應級別，不能用不同解析度直接排名。以下只是研究用共同規格。

| 項目 | 固定需求 |
| --- | --- |
| 畫面 | 主畫面、參數設定、趨勢、告警、維護，共 5 頁 |
| 基本操作 | 按鈕、切頁、數值輸入、滑桿、確認視窗與登入後操作限制 |
| 文字 | 繁體中文／英文切換、固定字型與字級；缺字、溢出及長字串案例 |
| 資料 | 20 個變數；先以 10 Hz 更新，再增加頻率觀察界線 |
| 趨勢 | 2 條曲線、每條 300 points，定義取樣與捲動方式 |
| 資產 | 相同圖像與色深，固定透明效果、動畫及更新範圍 |
| 通訊 | 對應方案的 UART／Modbus／CAN；用一致語意的主控模擬器 |
| 異常 | 封包截斷、無效值、掉線、重連、開機不同步及更新失敗 |

框架比較盡量採同一塊硬體、同一介面與相同視覺結果。智慧屏／晶片／模組比較應比較完整方案；有不同硬體優勢時，需連同 BOM 與配置說明，不把差異全部歸因於軟體。

## 實測項目與記錄方式

| 項目 | 方法與輸出 |
| --- | --- |
| 建置與重建 | 固定版本及編譯旗標，從乾淨環境重建；記錄失敗與手動步驟 |
| 開發工時 | 分開記畫面、控制邏輯、通訊、字型、部署、除錯；保留修改任務及投入者背景 |
| 記憶體與儲存 | 記錄 linker map、heap 高水位、stack 高水位與資產大小；智慧屏取得等效診斷資訊 |
| 效能 | 分別量測閒置、切頁、動畫、曲線與多變數更新；記錄 P50／P95 延遲及 CPU 負載 |
| 互動延遲 | 從輸入到畫面變更及控制器回覆分段測量；沒有內部 instrumentation 時用外部量測 |
| 通訊可靠性 | 記錄吞吐、bus load、重試、遺失、逾時與重連，不只記正常情境 |
| 穩定性 | 建議先做 24 小時反覆操作及資料更新，記錄 reset、停滯及記憶體成長 |
| 維護 | 修改共同元件、語言、資料地址，重新產生／部署，確認人工程式及既有行為保留 |
| 更新與遷移 | 測量資源／韌體更新時間、失敗復原、版本錯配，以及換 MCU 或模組所需工作 |

延遲與穩定性合格門檻應由實際產品需求設定；上述 24 小時為首輪研究設定，不等同量產驗證。未能取得的內部資源指標標為「無法取得」，不補成零。

### AI 與手動流程的比較

用相同初始專案，設計一組包含建頁、變更共享文字、加入圖像、變數綁定、邏輯分支及回復修改的任務。記錄首次完成率、人工修正時間、重試次數、成本、撤銷結果與非預期改動。模型名稱、版本、提示及設定應固定或完整記錄。

對有 AI 的工具比較「AI 加人工驗收」與其自己的手動流程；跨產品仍比較任務完成結果及總工時。沒有原生 AI 的產品不因此被記為 UI 功能不足。

## 執行前要固定的條件

1. 目標尺寸、解析度、觸控、電源、介面及環境條件。
2. 主控與顯示端的責任分配、資料字典、操作權限與更新機制。
3. Editor、框架、SDK、BSP、編譯器、資源格式及授權版本。
4. 同一工作負載、量測方法、成本邊界與比較級別。
5. 能交付的原始碼／專案／二進位、供貨與維護條件。

取得這些條件後再決定短名單。八項產品的下一步資料需求整理於[待確認事項](03-sources-and-open-questions.zh-TW.md)。
