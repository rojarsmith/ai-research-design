# VPS 上的最小平台建置路線與驗收

研究日期：2026-10-09。本路線以 New API 為最快的技術起點；公開 API 轉售須先有相應上游授權。未取得授權時，可用模擬上游或符合條款的內部用途驗證技術，不將封閉試用視為轉售限制的例外。

## 單台 VPS 架構

| 元件 | 職責 | 起步配置建議 |
| --- | --- | --- |
| Linux VPS | 執行代理與資料服務 | 2 vCPU、4 GB RAM 作為試用起點，SSD 約 40 GB；依負載調整 |
| HTTPS 反向代理 | TLS、請求大小限制、串流轉送 | Caddy 或既有 Nginx，確認不緩衝 SSE |
| New API | 會員、平台 Key、模型限制、額度與後台 | 單一固定版本的容器 |
| PostgreSQL | 使用者、額度、訂單與用量資料 | 持久化儲存，不公開資料庫埠 |
| Redis | 快取與限流 | 僅內網存取，設定認證 |
| 上游模型 API | 推論與上游成本 | Key 僅置於後端 channel，設定消費上限 |
| 異機備份與監控 | 資料還原、用量與可用性告警 | 備份帳本資料、設定與恢復所需的秘密 |

規格是工程起始估算，不是官方最低要求，也不是併發保證。主要壓力來自長連線數、寫入頻率、日誌與流量；要以 SSE 長連線實測，而非只看每秒短請求數。單台 VPS 仍有單點故障，適合初期驗證。

官方 Compose 範例使用 New API、PostgreSQL 與 Redis，包含示範密碼、`latest` 映像及對外 3000 埠。部署時應改成固定版本或 digest、隨機秘密與受限的網路暴露範圍。[官方 Compose](https://github.com/QuantumNous/new-api/blob/main/docker-compose.yml)

## 第一天建立內部示範

1. 在選定版本確認 LICENSE、NOTICE 與支付功能要求，記錄版本及映像 digest。
2. 依官方流程取得原始碼，修改 Compose，再啟動服務。使用 PostgreSQL 與 Redis；SQLite 單容器可做本機功能評估，持續收費平台採資料庫部署。
3. 設定網域 DNS 與 HTTPS。若代理在宿主機，應用埠只綁定 `127.0.0.1`；若代理在同一 Docker 網路，應用埠不用公開。初始化管理員後限制管理入口。
4. 產生並保存穩定的 `SESSION_SECRET`，設定 HTTPS 的 `SESSION_COOKIE_SECURE=true` 與精確的 `SESSION_COOKIE_TRUSTED_URL`；資料庫與 Redis 全部換掉示範密碼。
5. 新增 OpenRouter channel，僅在後台配置上游 Key。優先使用專用類型的預設網址；它的基底與最終 `/v1` 路徑由轉接器組合，不自行重複附加 `/v1`。
6. 選取當時可用的模型 ID，建立低額度測試使用者與平台 Key，完成一次非串流和一次 SSE 呼叫。

部署與 Cookie 設定依據：[官方 README](https://github.com/QuantumNous/new-api/blob/main/README.md)。Channel 與模型設定依據：[Channel 文件](https://docs.newapi.pro/zh/docs/guide/feature-guide/admin/channel)、[OpenRouter 類型原始碼](https://github.com/QuantumNous/new-api/blob/main/constant/channel.go)。

## 第一版的範圍

先做登入、Key 建立與撤銷、3 至 5 個文字模型、額度查詢、使用紀錄、管理員停用及上游餘額告警。設定每帳戶併發、輸出上限、Key 預算及平台每日總消費上限；新客戶使用較低上限。

起步不提供無限量方案。圖像、音訊、影片、長任務與 Responses 等接口逐項增加，每項都重新檢查相容性與計費。不要僅憑「OpenAI 相容」推定所有客戶端及所有端點均可使用。

## 三至七天完成封閉試用

在上游用途允許的前提下，邀請約 5 至 20 位測試者，先限制高價模型與最高單次成本。正式收款前可使用測試額度；人工付款確認與加額只適用於已有相應授權及收款條件的試營運，也要記錄付款與加額事件。

平台保存自己的售價表與生效時間。若 New API 按倍率與 token 計算售價，必須把平台扣款、上游回傳成本及上游帳戶扣款分開核對。預估值可做請求前限制，不能直接當作最終成本。

OpenRouter 現行用量文件描述：非串流回應附 usage，串流在最後 SSE 訊息附 usage，包含 cost、token、reasoning 及可用的 cache 資訊；也可透過 generation ID 非同步查詢。應以所用端點驗證欄位及幣別，再接入帳務。[用量核算文件](https://openrouter.ai/docs/cookbook/administration/usage-accounting)

對客戶額度的理想處理流程是「先保留預估額度，完成後依售價規則結算並釋放差額」。需驗證選定 New API 版本在併發、串流中斷、重試及批次更新下的實際行為；若不滿足，補做限制或改造帳務後才能擴大收款。

## 一至兩週接入自助收款

New API 支援多種支付介面，但可用方式取決於設定與版本的支付合規狀態。先確認營運主體所在地、收款商品與所選支付商的支援範圍，再決定接哪一家；不能因軟體含 Stripe 就推定你的主體一定能使用。[New API 錢包](https://docs.newapi.pro/zh/docs/guide/feature-guide/user/wallet)

以 Stripe 類型的回調為例，需驗證簽章，按付款物件與訂單去重，再於資料庫交易中一次完成「訂單標記已付款、增加額度、建立帳本記錄」。網頁跳回成功頁不能單獨觸發入帳。Stripe 明列事件可能重複與亂序，應設計重複及延遲回調處理。[Stripe Webhook](https://docs.stripe.com/webhooks)

使用現成付款模組也要跑驗收，不只測試付款成功。退款與拒付需要獨立狀態和記錄，平台規則須說明已使用服務與未使用額度如何處理；上游退款規則不會自動決定你的客戶退款義務。

## 最小驗收案例

| 案例 | 通過條件 |
| --- | --- |
| 餘額不足或 Key 已撤銷 | 拒絕新請求，未產生新的上游成本 |
| 同一帳戶同時送出多個請求 | 原子保留或其他可驗證限制避免反覆使用同一餘額；超用風險有明確界限 |
| 正常 SSE 與用戶中途斷線 | 回收連線與額度保留；已發生上游成本可結算或追查，不以未收到文字推定零成本 |
| 上游逾時但可能已處理 | 記錄待核對狀態；不盲目重試付費請求 |
| 閘道及上游各自設定重試 | 重試次數有界，能區分每次上游嘗試與一次客戶扣款 |
| usage 暫缺或售價未知 | 暫停未知模型或標記待結算，不無條件按零成本扣款 |
| 重複、延遲、亂序支付回調 | 同一付款只加額一次；重啟後也能去重並追查訂單 |
| 退款或拒付 | 有可追溯調整記錄，餘額與付款狀態一致 |
| 資料庫或 Redis 故障 | 帳務狀態不確定時拒絕新付費請求，恢復後可核對 |
| 異機備份還原 | 能重建使用者、Key 狀態、餘額、訂單及用量，無重複入帳 |

每日對帳分為兩條：客戶餘額須滿足「期初額度＋付款加額＋調整−售價扣款＝期末額度」；上游成本須核對「各請求實際成本合計」與「上游帳戶用量扣款變動」，另列充值與費用。差異須有原因，不能用客戶售價和上游成本直接相減當作對帳。

## 擴充觸發條件

當活躍 SSE 連線、資料庫寫入或備份窗口影響服務時，先測量瓶頸並調整，再拆分資料庫或增加代理節點。上游 Key 與管理 API 應始終由受限後端保管。公開模型清單由平台允許清單產生，避免客戶任意傳入未知高價模型或上游參數。

技術平台可以先建立；公開收款的完成時間則取決於上游書面授權、支付商資格、選定版本授權和上述驗收，不能以容器已啟動作為完成標準。
