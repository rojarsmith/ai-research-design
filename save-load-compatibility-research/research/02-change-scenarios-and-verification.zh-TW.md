# 功能變更的相容性策略與驗證

研究日期：2026 年 10 月 14 日。以下為建議工程政策與驗收案例。返回[主報告](../README.zh-TW.md)。

## 常見變更

| 變更 | 容易出現的問題 | 建議策略 |
| --- | --- | --- |
| 新增選填欄位 | 缺值被錯當成有效的零或 false | 指定歷史缺值語意；必要時保存 presence |
| 新增必要功能 | 舊版忽略後繼續操作造成錯誤 | 宣告 required feature，拒絕或唯讀 |
| 改欄位名稱 | 文字鍵或反射名稱不再相符 | 舊名稱 alias 或 migration；固定二進位 tag |
| 刪欄位 | 舊資料殘留、未來重用編號 | 棄用並保留編號；需要降版時保留舊表示 |
| 改數值型別 | 溢位、精度損失或符號改變 | 新欄位及檢查式轉換；定義越界政策 |
| 改單位 | 12 公分變成 12 公尺 | 依來源版本換算；新欄位標明單位 |
| 改 enum 順序 | 舊值讀成另一個狀態 | 固定明確數值；退役數值不再使用 |
| 拆分或合併類別 | 引用和身分無法接回 | 保留或映射舊 ID，明確定義所有權 |
| 修改預設值 | 舊檔缺值後改成新規則 | 舊版本補舊預設，新遊戲才用新預設 |
| 改世界生成器 | 同種子生成不同地形 | 生成器版本、已生成資料或內容遷移 |
| 改文件求值規則 | 數值相同但渲染或計算結果不同 | 規則版本、轉換或明確結果變更政策 |

Protobuf 的安全規則針對其二進位 wire format；換成 ProtoJSON 不能沿用全部結論。FlatBuffers 的 table 可以按規則演進，struct 則不能任意加減欄位。既有資料缺少欄位時，改預設值也可能改變解讀結果。[Protobuf](https://protobuf.dev/programming-guides/proto3/)、[FlatBuffers 演進](https://flatbuffers.dev/evolution/)、[FlatBuffers schema](https://flatbuffers.dev/schema/)

## 遊戲內容變更

任務 v1 需要交出十個蘋果，v2 改成五個梨子時，不應只用新的任務定義解釋舊計數。八個蘋果的進度要如何轉換，是內容設計決策：保留舊任務、按比例轉換、結算舊目標或提供補償都可，但需先選政策，再寫 migration。

物品「鐵劍」改顯示名稱時，`item_id` 保持不變。刪除物品時可使用替代映射、退役占位或補償；替代物品可能有不同的堆疊上限，轉換後還須處理超量背包、裝備限制及任務引用。不要默默把不存在的項目丟掉。

技能樹重寫可能無法保留節點的一對一關係。可重新發還投入的點數，保留補償紀錄與內容版本，避免每次載入重複補發。金錢與道具補償必須與版本升級在同一個提交邊界完成。

DLC 或模組移除時，先區分存檔是否依賴其世界與規則。可選外觀可用占位，必要關卡或腳本則可能阻止載入。把需求寫進 manifest，使玩家在載入前看到缺少的內容，而不是進世界後才遇到壞掉的引用。

OpenTTD 的載入後程式碼會根據舊版本補設定，並保留部分原有行為，說明新遊戲預設和歷史存檔預設應分別處理。[公開實作](https://github.com/OpenTTD/OpenTTD/blob/master/src/saveload/afterload.cpp)

## 軟體文件功能變更

3D 編輯器將材質節點改成新模型時，舊連接關系可能無法直接表示。可新增轉換節點、保留 legacy 求值器或烘焙結果，但烘焙會失去可編輯性；「畫面相同」和「仍可繼續編輯」是不同驗收條件。

CAD、排版或試算表的演算法修正也可能使舊檔重新計算結果改變。若產品重視既有結果，可記錄求值版本；若決定重新計算，則顯示轉換結果及變化摘要。快取只有在明確允許凍結結果時才能作為權威狀態，不能用舊快取掩蓋新模型的問題。

## 舊程式開新檔

對未來版本先檢查容器與能力宣告。已知布局、只有可選新增資料時，可允許讀取並保留未知區塊；缺少必要功能時拒絕或唯讀。未知容器布局就直接停止。

降版匯出要使用獨立轉換器，例如新材質轉成舊版支援的近似材質，並列出損失、另存副本。降低 `schema_version` 數字不會把資料還原成舊格式。舊版「能開啟」也不代表重存後仍保有新功能。

## 雲端與多裝置

建議保存文件 ID、唯一世代 ID、父世代及內容版本。若兩份資料有共同祖先但分別修改，應視為兩條分支；本機遞增計數及裝置時間都不能充分表達這種關系。

設定有時能逐欄合併，完整遊戲世界通常需要保留兩份並讓使用者選擇。不能同時拿 A 的背包與 B 的任務狀態，造成重複領獎或失去必要道具。離線分支更不能只用「較大遊玩時數」自動覆蓋另一份。

Steam 官方說明雲端檔案同步及衝突選項；世代與合並策略是這裡的應用設計建議。[Steamworks](https://partner.steamgames.com/doc/features/cloud?language=english)、[Steam Support](https://help.steampowered.com/en/faqs/view/68D2-35AB-09A9-7678)

## 驗證矩陣

設目前格式為 v3，最低支援格式為 v1。以下是測試計畫，不代表已有執行結果。

| 情境 | 應驗證的結果 |
| --- | --- |
| v1 直接升到 v3 | 完整跑 v1→v2→v3，貨幣及任務語意正確 |
| v2 升到 v3 | 不再執行貨幣倍率轉換 |
| v3 保存後載入 | 權威資料及共享引用一致，忽略合法快取差異 |
| v3 再次載入重存 | 不重複補償、不改身分、不再變更已遷移資料 |
| 未來容器版本 | 明確拒絕，原檔及目前世界不變 |
| 已知容器含未知必要功能 | 拒絕或唯讀，不丟資料再重存 |
| 可選未知欄位的 round-trip | 保留內容及適用的引用一致性 |
| 重複 ID、缺引用、超量資料 | 有限時間內失敗，不留下部分世界 |
| 寫入期間程序終止 | 恢復完整舊版或已提交新版，不採用半檔 |
| 磁碟滿、權限或刷新失敗 | 顯示保存失敗，已驗證存檔仍可恢復 |
| 舊非同步保存晚完成 | 不覆蓋後發且已成功的保存 |
| 遷移失敗或取消 | 升級前副本仍可用，不標示已升級成功 |
| 跨區域移動中保存 | 一個角色只有一個一致位置 |
| 缺 DLC 或外掛 | 指出依賴，按政策阻止或占位 |
| 雙裝置離線分支 | 保留衝突副本，不靜默覆蓋 |
| 跨平台讀取 | 編碼、數值、引用及路徑政策一致 |

歷史 fixtures 應來自真實舊版寫入器，包含一般數據與邊界資料；只用新版程式手造一份帶舊版本號的 JSON，會遺漏舊編碼器曾產生的布局與缺值行為。將保存樣本、寫入版本、預期遷移結果和必要資產一並管理。

## 測試方法

對 migration 做欄位及領域語意檢查，例如貨幣總量守恆、點數補償只發一次、父子關係合法。round-trip 比較正規化後的權威模型，允許保存時間、壓縮結果與快取變化；若格式沒有保證規範編碼，不能只比對整檔位元組。

故障注入覆蓋快照、暫存寫入、刷新、提交、備份與世代回收的各階段。程序崩潰測試不能取代真實斷電與平台耐久性測試。解析器另用 fuzzing 檢查損壞長度、壓縮炸彈、極深結構及惡意引用；讀取存檔不應任意實例化檔案聲明的程式類型或執行腳本。

量測完整鏈路的延遲和記憶體峰值，包括主執行緒擷取快照的時間；只有磁碟寫入改成非同步，並不能證明遊玩中的保存不會卡頓。

## 發版規則

每個持久資料變更應帶上 schema 差異、來源版本範圍、遷移政策、舊檔樣本及驗收結果。團隊可指定各模組的資料契約負責人，審核編號重複、單位變化和必要功能。

相容性停止支援時，先提供明確支援範圍、備份方式或中繼轉換工具。客戶端升級和資料升級是兩項操作；回退程式前要確認它能讀已升級資料，或恢復升級前副本。遷移完成並覆蓋舊資料後，並不能僅安裝舊程式就達成回退。
